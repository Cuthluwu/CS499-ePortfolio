Artifact and selection

The original artifact is a Java service suite created in May 2026 for CS 320 Software Testing, Automation, and Quality Assurance. It contains contact, task, and appointment models, three in-memory services, and JUnit tests for the required field limits and CRUD behavior. Each service stores records in a HashMap keyed by an immutable identifier.

I selected it because a small codebase makes design decisions easy to isolate. The original already demonstrated input rules, collection use, unique identifiers, and testing. It also exposed meaningful weaknesses: the folders did not share a package or contract, validation was repeated, missing records had inconsistent behavior, mutable objects crossed the service boundary, and a multi-field update could change one value before a later validation failure. Those were architectural problems, not formatting problems.

Module One initially named the CS 250 SNHU Travel planning work for this category. The code review showed that those materials remained useful Agile and stakeholder context but did not provide enough source for a code-level walkthrough. I documented the refinement and used the CS 320 suite as the concrete technical artifact.

Baseline analysis

The original addContact method stores the caller's exact object, and getContact returns the same stored reference. The caller can therefore change service state later through a setter without invoking the service. Retrieval returns null for absence, while deletion goes through a private method that throws a general IllegalArgumentException. Every caller has to remember a different absence policy.

The appointment model protects its inner Date less consistently than a modern service boundary should, and validation depends on moving system time. A test near the present-time boundary can fail according to when the assertion executes. The repeated patterns across services also make it easy for policies to drift.

Before and after: service ownership

Original

public void addContact(Contact contact) {
    if (contacts.containsKey(contact.getContactId())) {
        throw new IllegalArgumentException(
            "A contact with this ID already exists.");
    }
    contacts.put(contact.getContactId(), contact);
}

public Contact getContact(String contactId) {
    return contacts.get(contactId);
}

Enhanced

public void add(Contact contact) {
    if (contact == null) {
        throw new IllegalArgumentException(
            "Contact cannot be null.");
    }
    String identifier = contact.getContactId();
    if (contacts.containsKey(identifier)) {
        throw new DuplicateRecordException(
            "Contact", identifier);
    }
    contacts.put(identifier, new Contact(contact));
}

public Optional<Contact> findById(String identifier) {
    String normalized = Validation.identifier(
        identifier, "Contact ID");
    return Optional.ofNullable(contacts.get(normalized))
        .map(Contact::new);
}

The enhanced add path rejects null, assigns a specific duplicate policy, and stores a copy. The read path validates the identifier, expresses ordinary absence through Optional, and returns a snapshot. The map remains the service's state rather than becoming a collection of shared object references.

Atomic multi-field updates

updateName creates a copy of the stored contact, validates both new values on that copy, and writes the replacement only after both setters succeed. If last-name validation fails, the original first name remains unchanged. Similar copy-validate-replace logic protects task and appointment updates. Focused checks read the record after an exception and confirm that the stored postcondition remains unchanged.

Verification

The enhanced Maven project contains 97 JUnit methods across 12 test classes. Six classes retain the original requirements; the additional tests cover shared validation, exact exception policies, defensive copying, failed-update atomicity, controlled time, and the common repository contract. A separate executable verifier performed 26 focused checks and recorded a passing result for every one.

Executed evidence: 26 of 26 focused software-design checks passed. The technical package also includes the Maven project, JUnit sources, original integrity hashes, enhancement map, full original-to-enhanced diff, and verification output.

Reflection

The most important lesson was that encapsulation can fail even when fields are private. If a service stores and returns the same mutable object, external code still controls the service's state. Defensive copying at both sides of the boundary made the ownership rule concrete.

I also learned to distinguish lookup from command failure. A missing search result is normal and can be represented explicitly. An update or delete that cannot act on the requested identifier is a failed command and should say why. That difference made the service API easier to reason about and test.

I considered a generic base-service class but rejected it. The services share repository operations, yet their update behavior and later retrieval algorithms differ. A small interface documents the common contract without forcing unrelated implementation details into an inheritance hierarchy.

The remaining limitations are intentional and documented. The services are in-memory, single-process teaching components. They do not claim persistence, thread safety, authentication, or authorization. Those concerns belong to a different layer and appear in the database artifact rather than being hidden behind a more complicated abstraction here.
