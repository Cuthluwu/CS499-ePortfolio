Software Design and Engineering

CS 320 Contact, Task, and Appointment Services

I went back to an earlier Java project and focused on making the code easier to maintain, test, and reason about.

Download the narrativeMilestone reflection and references Download the artifactOriginal and enhanced project Original ContactServiceCS 320 version Enhanced ContactServiceCS 499 version

Why I chose this project

This project came from CS 320. It contains contact, task, and appointment classes, service classes, and JUnit tests. The original version worked for the course requirements, but the three services repeated a lot of the same ideas and handled errors differently.

I chose it because the code was small enough that I could clearly show the difference between simply making something work and making it easier to maintain. I also wanted to improve an older project instead of replacing it with something completely new.

What I changed

AreaChange
Project structureMoved the code into one Maven project with clear packages for models, services, validation, repositories, and exceptions.
ValidationMoved repeated validation rules into shared code instead of copying the same checks into several classes.
Stored objectsAdded defensive copies so outside code cannot change a stored object without going through the service.
UpdatesChanged multi-field updates so a failed validation does not leave half of the update applied.
Missing recordsMade lookup and command failures more consistent instead of mixing null values and general exceptions.
Date testingAdded a controllable clock so appointment tests do not depend on the exact current time.

Example: protecting stored data

Original

public void addContact(Contact contact) {
    contacts.put(contact.getContactId(), contact);
}

public Contact getContact(String contactId) {
    return contacts.get(contactId);
}

Enhanced

public void add(Contact contact) {
    String id = contact.getContactId();
    if (contacts.containsKey(id)) {
        throw new DuplicateRecordException("Contact", id);
    }
    contacts.put(id, new Contact(contact));
}

public Optional<Contact> findById(String id) {
    return Optional.ofNullable(contacts.get(id))
        .map(Contact::new);
}

The important difference is that the service no longer keeps and returns the exact object that another part of the program gave it. That makes the service responsible for its own data instead of allowing outside code to change it accidentally.

Testing

I kept the original tests and added tests for the new behavior. I specifically checked copying, invalid updates, duplicate records, missing records, shared validation, and appointment dates. I also used a small focused verifier while reviewing the final code.

What I learned

The biggest lesson from this enhancement was that private fields alone do not guarantee good encapsulation. If a service stores the same mutable object it receives and then gives that same object back, other code can still change its state.

I also became more careful about updates. In the original style of code it was possible to change one field and then fail while validating the second field. Copying the object first and replacing the stored version only after the full update succeeds is safer and easier to test.

I did not try to turn this into a production framework. It is still an in-memory school project. My goal was to improve the structure and behavior without hiding what the project actually is.

Program outcomes

This artifact mainly supports the outcomes for software-development techniques, communication, collaboration habits, and security. The clearest examples are the improved project structure, shared rules, more predictable service behavior, added tests, and protection against unintended changes to stored data.
