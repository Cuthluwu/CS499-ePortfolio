Software Design and Engineering

CS 320 Contact, Task, and Appointment Services

I went back to an earlier Java project and focused on making the code easier to maintain, test, and understand.

Why I chose this project

This project came from CS 320. It contains contact, task, and appointment classes, service classes, and JUnit tests. The original version worked for the course requirements, but looking at it again showed me several places where similar rules were repeated and where the service behavior could be clearer.

I chose it because the code was small enough to compare directly before and after. I also wanted to improve an older project instead of replacing it with something completely new.

What I changed

AreaChange
Project structureMoved the code into one Maven project with packages for models, services, validation, repositories, and exceptions.
ValidationMoved common checks used by the model classes into shared validation methods.
Stored objectsAdded copies so outside code cannot change a stored object just by keeping or receiving a reference to it.
UpdatesAdded combined update methods that validate a copied object before replacing the stored version.
Missing recordsChanged direct lookups to use Optional and used specific exceptions for missing or duplicate command operations.
Date testingAdded a controllable clock so appointment tests do not depend on the exact current time.

Example: protecting stored data

Original

public void addContact(Contact contact) {
    if (contact == null) {
        throw new IllegalArgumentException(
            "Contact cannot be null.");
    }

    if (contacts.containsKey(contact.getContactId())) {
        throw new IllegalArgumentException(
            "A contact with this ID already exists.");
    }

    contacts.put(contact.getContactId(), contact);
}

public Contact getContact(String contactId) {
    return contacts.get(contactId);
}

Enhanced

public void add(Contact contact) {
    String id = contact.getContactId();
    if (contacts.containsKey(id)) {
        throw new DuplicateRecordException("Contact", id);
    }
    contacts.put(id, new Contact(contact));
}

public Optional<Contact> findById(String id) {
    return Optional.ofNullable(contacts.get(id))
        .map(Contact::new);
}

The original service already checked for a null contact and duplicate IDs. The problem I focused on here is different: after those checks, it stored the same mutable Contact object it received and returned that object from getContact(). In the enhanced version, the service stores a copy and returns a copy, so outside changes do not automatically change the record held by the service.

Testing

I kept the original test ideas and added tests for the behavior I changed, including copying, invalid updates, duplicate and missing records, shared validation, and appointment dates. The repository also contains a small Java verification script used during the final review.

What I learned

The biggest lesson from this enhancement was that private fields alone do not guarantee good encapsulation. If a service stores the same mutable object it receives and gives that same object back, other code can still change the service's data.

I also thought more carefully about updates when I added methods that can change more than one field. I wanted the whole change to be valid before replacing the stored record, instead of saving part of a change first.

I did not try to turn this into a production framework. It is still an in-memory school project. My goal was to make a project I had already written cleaner and safer while keeping its original purpose recognizable.

Program outcomes

This project connects most clearly to software-development techniques, communication, and the security mindset outcome. The changes I can point to are the reorganized project, shared validation, clearer missing-record behavior, added tests, and storing and returning copies instead of the same mutable objects.
