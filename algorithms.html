Artifact and category boundary

The artifact is the same Java service suite created in May 2026 for CS 320 and reorganized during Category One. Reusing it is deliberate: the software-design foundation remains stable while the new work addresses a different question. Category One owns packages, validation, service contracts, state protection, atomic updates, and controlled time. Category Two adds four production deltas: shared search-term validation and one retrieval algorithm for each service.

The technical package makes this cumulative history visible. It contains the unchanged original CS 320 source, the Week 3 design baseline, the Week 4 algorithm-enhanced source, a focused Week 3-to-4 diff, documentation, and executable evidence. This prevents the earlier design work from being counted again as though it were a new algorithm enhancement.

Data-structure decision

HashMap remains the backing structure because the primary service operations address records by unique identifier. Under normal hash distribution, add, find, update, and delete by ID have expected O(1) behavior. Replacing the map solely to obtain display order would move ordering cost into every mutation and would not solve arbitrary substring search.

Each broader query instead traverses the values, filters the matches, copies each result, sorts only the matches, and returns an unmodifiable list. The design has one source of truth and keeps ordering specific to the caller's need. Secondary indexes remain a reasonable future choice only if data volume and profiling justify their update and memory costs.

Before and after: contact retrieval

Week 3 baseline

public Optional<Contact> findById(
        String identifier) {
    String normalized = Validation.identifier(
        identifier, "Contact ID");
    return Optional.ofNullable(
        contacts.get(normalized))
        .map(Contact::new);
}

// No cross-record contact search.

Week 4 enhancement

public List<Contact> searchByLastName(
        String query) {
    String normalized = Validation.searchTerm(
        query, "Last-name search")
        .toLowerCase(Locale.ROOT);
    return contacts.values().stream()
        .filter(contact -> contact.getLastName()
            .toLowerCase(Locale.ROOT)
            .contains(normalized))
        .map(Contact::new)
        .sorted(SEARCH_ORDER)
        .toList();
}

The algorithm does not depend on map iteration order. It normalizes the query once, matches without locale-sensitive case errors, copies results before returning them, and establishes a complete comparator chain so equal last names still have a predictable order.

Inclusive appointment range

Category Two implementation

public List<Appointment> findByDateRange(
        Date startInclusive, Date endInclusive) {
    if (startInclusive == null || endInclusive == null) {
        throw new IllegalArgumentException(
            "Start and end dates are required.");
    }
    long startMillis = startInclusive.getTime();
    long endMillis = endInclusive.getTime();
    if (startMillis > endMillis) {
        throw new IllegalArgumentException(
            "Start date cannot be after end date.");
    }

    return appointments.values().stream()
        .filter(item -> item.getAppointmentTimeMillis()
                >= startMillis
            && item.getAppointmentTimeMillis()
                <= endMillis)
        .map(Appointment::new)
        .sorted(DATE_ORDER)
        .toList();
}

The method reads each range bound into an immutable primitive timestamp, rejects an inverted interval, includes appointments on either boundary, copies every matching model, and orders equal dates by identifier. A no-match query returns an empty unmodifiable list, not null.

Complexity and trade-offs

OperationExpected timeAdditional result space
Exact-ID map accessO(1) expectedO(1)
Contact last-name searchO(c + n + m log m)O(m)
Task keyword searchO(c + n + m log m)O(m)
Appointment date rangeO(c + n + m log m)O(m)

Here, c is current map capacity, n is stored records, and m is matches. A no-match search still traverses the map but creates no snapshots and sorts an empty result. A query matching every record reaches O(c + n log n) time with O(n) result space. Filtering before sorting avoids comparisons for records that do not match.

The final performance pass preserves those bounds while reducing temporary allocation. Comparator chains are reusable class constants; Java 17's Stream.toList() already returns an unmodifiable result, so the methods do not copy the completed list a second time; and appointment filtering and sorting use primitive timestamps instead of repeatedly allocating defensive Date copies. The defensive copy of every returned model remains in place.

A TreeMap keyed by last name would not make arbitrary substring matching constant time. An inverted task index would need tokenization and synchronization rules. A date index could locate a range more directly but would add duplicate-key and rescheduling maintenance. Those are appropriate alternatives only when an observed workload justifies their extra invariants.

Reflection

The main correction to my earlier thinking was separating map lookup from map traversal. Saying “the service uses a HashMap, so access is constant time” is only accurate for identifier operations. Search across values is linear before sorting costs are considered. Writing the bounds forced me to connect each claim to the actual code path.

Deterministic order also became part of correctness. A collection can contain the right matches and still produce an unstable interface or a flaky test if equal primary fields have no tie-breaker. The final comparators continue until the immutable identifier, so the result contract is complete.

Finally, immutability required two decisions. Stream.toList() prevents structural changes to the returned list, but it does not protect mutable objects inside that list. Copying each model before sorting and returning it is what prevents a caller from using a result element to alter service state.
