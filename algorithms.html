Algorithms and Data Structures

Search, filtering, and ordering in the CS 320 services

This enhancement adds ways to search the service data when the exact record ID is not already known.

Why I continued with the same project

I used the same CS 320 project from Category One because it let me focus on a different problem without changing the whole codebase again. The first enhancement dealt with structure and service design. This one deals with how records are found when the caller does not already know the exact ID.

Why I kept HashMap

The services already use a HashMap keyed by ID, and that still makes sense for exact lookups. Finding a contact by its ID is different from searching every contact by last name. I kept the map for the operations it is good at instead of replacing it just to make one new feature easier.

For the broader searches, the service walks through the stored values, keeps the matches, sorts those matches, and returns the results. That is simple and reasonable for this small in-memory project.

Example: contact search

public List<Contact> searchByLastName(String query) {
    String normalized = Validation.searchTerm(
        query, "Last-name search")
        .toLowerCase(Locale.ROOT);

    return contacts.values().stream()
        .filter(contact -> contact.getLastName()
            .toLowerCase(Locale.ROOT)
            .contains(normalized))
        .map(Contact::new)
        .sorted(SEARCH_ORDER)
        .toList();
}

The search is not constant time just because the service uses a HashMap. It still has to look through the stored contacts. That distinction was one of the main things I wanted to show in this milestone.

Complexity

Exact-ID access is expected O(1). The new searches are different because they scan the collection and then sort the matches. I describe that as O(n + m log m), where n is the number of stored records and m is the number of matches. The returned results also use O(m) additional space.

I considered extra indexes, but I did not think they were justified for a small classroom collection. An index could make some searches faster, but it would also add more code that has to stay synchronized every time a record changes.

Testing

I added tests for mixed-case searches, no-match results, blank search terms, inclusive appointment dates, invalid ranges, ordering, and returned-list behavior. I also checked that changing a returned object does not change the object stored by the service.

What I learned

The biggest correction I made was to my own explanation of performance. Earlier in the program I could look at a HashMap and say that it was fast without separating exact-key access from a full search through its values. This milestone made me connect the complexity statement to the actual method.

I also learned that sorting is part of the behavior of a search feature. If two contacts have the same last name, the result should still be predictable. Adding tie-breakers to the comparators made the output more stable and made the tests more reliable.

I kept the solution simple on purpose. A more complicated data structure is not automatically a better choice if the project does not need it.

Program outcomes

This project is my clearest example for the algorithms and data structures outcome. It shows the difference between key lookup and collection search, includes complexity analysis, and explains why I kept the existing map instead of adding extra indexing without a clear need.
