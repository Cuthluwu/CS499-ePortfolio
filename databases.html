Artifact and selection

The artifact is the Android Weight Tracker I created in June 2026 for CS 360 Mobile Architecture and Programming. It uses Java activities, XML layouts, and local SQLite storage for registration, login, and weight CRUD. I selected it because persistence is the application's central responsibility. The product succeeds only if it can store multiple measurements, associate them with the correct account, order them, update the intended row, preserve them through an upgrade, and summarize progress accurately.

The original is preserved without modification. The enhanced work lives in a separate Android Studio project. Documentation and evidence are separate from both source trees, so an instructor can compare the actual baseline to the final implementation without guessing which files changed.

Original condition

  • Credential exposure: the users table stores passwords as plaintext, and login compares the submitted value directly in SQL.
  • No record ownership: Userdetails has no account identifier or foreign key; history returns every row.
  • Wrong row identity: a name is the primary key, so the same person cannot have a realistic series of measurements.
  • Weak types: weight and date are unrestricted text.
  • Destructive lifecycle: onUpgrade drops both tables.
  • Thin evidence: template tests do not check schema, ownership, security, ordering, migration, or reporting.

Before: schema and upgrade

Original DBHelper.java

public void onCreate(SQLiteDatabase database) {
    database.execSQL(
        "create Table users(" +
        "username TEXT primary key, password TEXT)");
    database.execSQL(
        "create Table Userdetails(" +
        "name TEXT primary key, weight TEXT, date TEXT)");
}

public void onUpgrade(SQLiteDatabase database,
        int oldVersion, int newVersion) {
    database.execSQL("drop Table if exists users");
    database.execSQL("drop Table if exists Userdetails");
}

Normalized version-two schema

The new model separates accounts from measurements. A numeric user_id identifies an account, and each weight_entries row has its own numeric entry_id plus a required account foreign key. Weight has REAL affinity, dates use ISO YYYY-MM-DD, and constraints reject invalid states at the database boundary.

Enhanced DatabaseContract.java

CREATE TABLE weight_entries (
    entry_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    weight REAL NOT NULL
        CHECK(weight > 0 AND weight <= 1500),
    entry_date TEXT NOT NULL
        CHECK(length(entry_date) = 10
            AND date(entry_date) = entry_date),
    note TEXT NOT NULL DEFAULT ''
        CHECK(length(note) <= 250),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(user_id) REFERENCES users(user_id)
        ON DELETE CASCADE
);

CREATE INDEX idx_weight_entries_user_date
ON weight_entries(user_id, entry_date DESC, entry_id DESC);

Foreign-key enforcement is enabled in DBHelper.onConfigure() for every connection. ON DELETE CASCADE prevents orphaned measurements. Java validation produces understandable messages before a write, while NOT NULL, UNIQUE, CHECK, and foreign-key constraints remain the final protection against invalid state.

Credentials, authentication, and authorization

The enhanced password helper uses PBKDF2-HMAC-SHA-256 with a unique 16-byte salt, a 256-bit derived value, and 600,000 iterations. The database stores the Base64 hash, salt, algorithm, and work factor. Authentication retrieves one verifier record and uses MessageDigest.isEqual for comparison. Password character arrays are cleared after use.

The final capstone pass tightened two edge cases found during review. Blank legacy credentials had been replaced with a predictable username-derived value, and damaged iteration metadata could request an unreasonable amount of PBKDF2 work. The final code creates an independently randomized 256-bit inaccessible credential for a blank legacy value, rejects iteration counts above 1,200,000, and checks decoded salt and hash dimensions before derivation.

This remains a classroom-local identity design, not a complete production platform. The artifact does not claim account recovery, breach-password screening, server-side throttling, a hardware-protected pepper, or encrypted database storage.

Ownership-scoped CRUD

Authentication establishes the current user_id. Authorization continues inside every measurement operation. Update and delete conditions require both the row ID and the authenticated owner ID:

Ownership condition

UPDATE weight_entries
SET weight = ?, entry_date = ?, note = ?, updated_at = ?
WHERE entry_id = ? AND user_id = ?;

DELETE FROM weight_entries
WHERE entry_id = ? AND user_id = ?;

A user who learns another row's numeric identifier still receives a zero-row result. Registration no longer opens the dashboard directly; a new account returns to login, and only successful authentication supplies the stable account session.

Data-preserving migration

The database version rises from one to two. Upgrade renames the legacy tables, creates the complete version-two schema, converts accounts, normalizes readable measurements, records migration problems, and drops the renamed tables only after conversion completes. The callback runs inside the transaction managed by SQLiteOpenHelper, so a structural failure rolls back instead of leaving half of the new schema.

The original database never recorded an account ID for a weight row, so perfect ownership cannot be reconstructed. The migration uses one conservative rule: an exact case-insensitive name-to-username match may establish ownership. A readable unmatched row is preserved under a separate import account, and an unreadable date or weight is written to migration_issues with the original values and a reason. The migration does not guess which real user owns ambiguous health data.

History, index, and progress value

History filters by authenticated user_id and orders by date descending, then entry ID descending. The tie-breaker makes same-date output deterministic. The latest query uses the same order with LIMIT 1. The progress summary returns count, first measurement, latest measurement, and the signed change between those endpoints; an empty history produces a zero-count summary.

The compound index follows the actual access path: account restriction first, then the requested date and entry-ID order. The verification harness uses EXPLAIN QUERY PLAN and confirms that SQLite selects this index. I did not index note or weight because the application does not query globally by those fields; unnecessary indexes would increase write and storage cost.

Reflection and response to feedback

The largest conceptual change was learning that persistence does not automatically mean good database design. The original project stored information, but one row did not represent a well-defined measurement owned by a well-defined account. Redesigning the meaning of each key and relationship mattered more than adding another button.

The migration was the hardest part because the old schema did not contain enough ownership information. Assigning every row to the first account would have made the demonstration look complete while inventing private data. The import-account and audit-table approach is less convenient, but it preserves what can be proven and makes uncertainty visible.

Testing changed the implementation. Cross-user tests forced ownership into the SQL WHERE clause. Same-date checks required the entry-ID tie-breaker. Invalid legacy data led to the migration audit table. The final security review exposed the guessable blank-password fallback and the unbounded work factor. Those findings are examples of verification improving the design rather than simply confirming it.

Earlier feedback and file-delivery problems also changed the packaging. The artifact now opens to a read-first guide, separates original and enhanced projects, includes exact evidence locations, keeps the narrative outside the technical ZIP, and distinguishes executed checks from included Android tests. Professional communication includes whether a reviewer can actually find and open the work.

The main remaining engineering limitation is synchronous database work from an activity. A production revision should move I/O off the main thread or adopt Room with lifecycle-aware components. Other future work includes account recovery, rate limiting, encrypted sensitive storage, and a deliberate reminder feature rather than an unused permission.
