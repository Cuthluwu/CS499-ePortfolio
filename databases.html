Databases

CS 360 Android Weight Tracker

I used this project to improve the database structure, connect records to users, and fix several security and migration problems from the original version.

Why I chose the Weight Tracker

The Weight Tracker came from CS 360. The original application used Java activities, XML layouts, and SQLite for registration, login, and weight records. I chose it because the database is central to the application. If the data is stored incorrectly, attached to the wrong account, or lost during an update, the rest of the app does not matter much.

Problems in the original database

  • Passwords were stored as plain text.
  • Weight rows were not tied to a specific user account.
  • A name was used as the primary key for a weight record.
  • Weight and date were stored as unrestricted text.
  • The history query could return records from every user.
  • The database upgrade method dropped the existing tables.

These were more than formatting issues. They affected privacy, data integrity, and whether the application could realistically store a history of measurements.

Schema changes

The enhanced version separates users from weight entries. Users have a numeric user_id, weight records have a numeric entry_id, and every weight record contains the ID of its owner. A foreign key connects the two tables.

Weight is stored as a numeric value instead of free-form text, and dates use a consistent YYYY-MM-DD format. I also added database constraints so obviously invalid values can be rejected even if a future screen forgets to validate them first.

CREATE TABLE weight_entries (
    entry_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    weight REAL NOT NULL CHECK(weight > 0 AND weight <= 1500),
    entry_date TEXT NOT NULL,
    note TEXT NOT NULL DEFAULT '',
    FOREIGN KEY(user_id) REFERENCES users(user_id)
        ON DELETE CASCADE
);

Password and account changes

The original project stored passwords directly in SQLite. The enhanced version uses PBKDF2 with a random salt and stores the resulting hash information instead of the original password. I also changed the login flow so successful authentication is what establishes the current user session.

Weight updates and deletes include both the entry ID and the current user ID in the database condition. That means knowing another row's numeric ID is not enough to change it.

UPDATE weight_entries
SET weight = ?, entry_date = ?, note = ?, updated_at = ?
WHERE entry_id = ? AND user_id = ?;

This is still a classroom application, not a complete production identity system. A real release would need more work around account recovery, rate limiting, encrypted device storage, and application lifecycle behavior.

Migration

The original onUpgrade() deleted the tables. I changed the database version and added a migration that renames the old tables, creates the new schema, and then moves usable data into the new format.

The difficult part was that the old weight table did not actually store a user ID. That means there is no perfect way to reconstruct ownership for every old record. When a record can be matched safely, the migration uses that account. Readable records that cannot be matched are kept under a separate import account instead of being assigned to a random person. Values that cannot be converted are recorded in a migration-issues table.

This was one of the more important decisions in the project because it would have been easy to make the migration look complete by guessing. I would rather preserve uncertainty than silently attach private data to the wrong user.

History and reporting

The history query now filters by the current user_id and sorts by date, with the entry ID used as a tie-breaker when two records share a date. I also added a compound index that starts with the user ID because every history request belongs to one account.

The project includes a progress summary based on the first and latest measurements. I kept the query work focused on what the application actually uses instead of adding indexes for fields that are never searched globally.

Testing

I added checks for the schema, constraints, account ownership, weight CRUD, history order, migration, password verification, and invalid data. The repository also contains Android test source for the project. During the final preparation pass I did not claim a full Android APK build from an environment that did not have the Android SDK available.

What I learned

The biggest lesson from this milestone was that using a database does not automatically mean the data model is good. The original project could save rows, but the rows did not have a clear relationship to the account that owned them. Fixing the meaning of the tables was more important than adding another screen or feature.

I also learned that migration exposes weaknesses in the original design very quickly. If an old schema never stored a relationship, new code cannot magically recover it later. That made me think more carefully about what information needs to be represented when the schema is first designed.

The security work changed the project in practical ways too. Replacing plain-text passwords was important, but it was not enough by itself. User ownership also had to be enforced in the database operations, and the project still has limitations that would need to be addressed before a real release.

Program outcomes

This artifact is my strongest example for the security outcome and also supports the software-development and algorithms outcomes. It shows relational database design, migration, account ownership, password handling, query ordering, indexing, and testing inside one application.
