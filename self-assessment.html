Looking Back at the Program

When I started the computer science program, I thought mostly in terms of finishing one assignment at a time. I would focus on getting a screen to work, getting a method to return the right value, or getting a database query to run. By the end of the program, I was looking at those pieces together. I became more aware of how one decision affects the rest of an application, especially when data moves between an interface, program logic, and a database.

The capstone made that change very obvious to me because I had to return to projects I had already completed. Some of the code that felt finished when I first submitted it looked different after another year of classes. I could see repeated validation, weak database relationships, unclear error behavior, and places where the code technically worked but could be easier to maintain. That was probably the most useful part of the course for me. I was not starting from a blank project. I had to look at my own older work, decide what was actually worth changing, and explain why.

Professional Direction and Strengths

I am most interested in application development, especially work that connects a user interface to program logic and stored data. Full-stack and mobile development both interest me because I like seeing how a user action travels through the rest of a system instead of only working on one isolated piece.

One strength I developed is being willing to revisit code instead of treating a completed assignment as untouchable. The CS 320 project is a good example. The original version met the course requirements, but during the capstone I could see that the three services repeated rules and exposed mutable objects in ways I had not thought much about before. In the enhanced version I reorganized the project, shared validation, protected stored objects with copies, and changed how updates are applied.

Another strength is testing. CS 320 originally taught me to think about requirements as things that should be checked, not just written down. I carried that into the capstone by adding tests around the exact behavior I changed. I still have room to improve here, especially with larger integration tests and Android testing, but I am much less likely now to assume that code is correct because it compiled or worked once.

Collaboration and Communication

Most of the projects in this ePortfolio were individual assignments, so my strongest collaboration examples come from the habits I practiced in courses such as CS 250. User stories, acceptance criteria, sprint planning, and retrospectives helped me understand why software work has to be understandable to people besides the person who wrote it.

I tried to use that lesson in the capstone by keeping the original projects separate from the enhanced versions and organizing the repository so someone can compare them. I also changed my original artifact plan when I realized the CS 250 planning material did not give me enough code for the software-design enhancement. Instead of forcing it to fit, I used the CS 320 service project and kept the CS 250 work as part of the discussion about planning and collaboration.

Communication is also more than writing technical terms correctly. In CS 465, I had to think about a travel application that served public users differently from administrators. In DAT 205, the meaning of a report depended on how terms and limits were explained. Those experiences made me more careful about explaining what a project does in normal language before getting into implementation details.

Algorithms and Data Structures

The algorithms milestone showed me that naming a data structure is not the same thing as explaining performance. The CS 320 services use a HashMap, which is useful for looking up an item when the ID is already known. That does not mean a search across every stored contact or task is constant time.

For the enhancement I kept the map for exact-ID operations and added searches that scan the stored values, keep the matching records, and sort the results. Writing the complexity analysis made me separate those cases instead of describing the whole service as fast because it uses a hash-based collection. I also paid more attention to stable ordering so two records with the same main sort field still return in a predictable order.

Software Engineering and Databases

The biggest software-engineering lesson for me was responsibility. In the enhanced CS 320 project, validation should have a clear place, services should control their own stored state, and an update should either succeed as a whole or leave the old record alone. Those ideas sound simple, but the original project showed how easy it is to blur those responsibilities in a small program.

The Weight Tracker pushed the same lesson further because database mistakes survive after the program closes. The original version stored passwords as plain text, used text fields for weight and date, and did not connect weight rows to a specific account. The enhanced version gives users and entries numeric IDs, connects entries to users with a foreign key, stores weight as a number, uses normalized dates, and changes the upgrade process so it attempts to preserve existing data instead of simply dropping the tables.

I also learned that migration is not just a technical problem. The old database did not contain enough information to know the owner of every existing weight row. Rather than inventing ownership, the enhancement keeps unmatched readable records under a separate import account and records values that cannot be safely converted. That was a better solution than pretending the old data contained information it never stored.

Security

Security became more concrete for me during the database enhancement. The original login code stored and compared plain-text passwords. The enhanced project uses PBKDF2 with a salt instead. Weight operations also include the current user ID so one account cannot update or delete another account's entry just by knowing its row ID.

I do not consider the project a finished production authentication system. It is still a local classroom application. There are features a production app would need, such as account recovery, rate limiting, stronger device storage protections, and more complete lifecycle handling. What changed in my thinking is that I now look for those limitations instead of calling an application secure because I added one security feature.

What the Three Artifacts Show

The three enhancement categories show different parts of the same growth. The software-design work is about organizing responsibilities and protecting state. The algorithms work is about matching a solution to the way data is accessed and being accurate about complexity. The database work is about persistent data, relationships, migration, and security.

I also think the before-and-after structure matters. I did not want the ePortfolio to only show polished final code. Keeping the original versions makes the improvement visible and reminds me that development is usually iterative. The earlier projects were not useless because they had weaknesses. They were the starting point that made the later changes possible.

Program Outcomes and Next Steps

The capstone gave me examples for all five program outcomes. Collaboration is represented by Agile coursework and by making changes reviewable. Communication is represented by the narratives, code review, and ePortfolio. Algorithms and data structures are most visible in the Week 4 search work. Techniques and tools appear across Java, Maven, Android, SQLite, testing, Git, and GitHub Pages. Security is strongest in the Weight Tracker enhancement and in the state-protection work from CS 320.

I am leaving the program with a much better understanding of what I still need to learn. I want more experience with larger projects, team-based development, deployment, backend services, and production testing. I also want to keep improving the way I document decisions without overcomplicating the documentation itself.

The main thing I take from this capstone is that being a better developer does not mean never writing weak code. It means being able to recognize problems, improve them, test the result, and explain the choices clearly. Comparing my original coursework with the enhanced artifacts gave me a concrete way to see that progress.
