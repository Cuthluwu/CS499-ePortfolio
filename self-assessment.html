Professional Identity, Strengths, and Direction

I entered Southern New Hampshire University's computer science program on May 3, 2025, wanting to understand how complete applications are built. At that point, I could focus on a screen, a method, or a database operation as a separate task. My strongest growth has been learning to treat those pieces as one system. A useful application has to translate a person's need into a clear requirement, choose an appropriate structure, protect the data that crosses each boundary, verify the result, and explain the decision to someone who did not write the code.

My professional direction is practical application development, with an emphasis on full-stack and mobile systems. I am most engaged by work in which a user action travels through an interface, a service or controller, and a persistent data layer. That interest does not mean I treat the interface as the entire product. The program taught me to examine state ownership, failure behavior, data relationships, query cost, migration, authentication, authorization, and test evidence. I now approach an application as a set of contracts: what the user is allowed to submit, what the software promises to preserve, what each layer owns, and what evidence supports the result.

One of the biggest changes in my work is that I can go back to old code without pretending it was better than it was. I keep the original version, name the problems I found, and make changes that affect behavior instead of only changing how the project looks. I also turn requirements into checks. Field limits, ownership rules, ordering, error behavior, and security assumptions should be testable. When something is outside the project, I say so. Password hashing is not encryption, a local SQLite app is not a production identity platform, and the Bluetooth idea is not finished code.

My values as a developer are reliability, clarity, privacy, and respect for the user. Reliability means that failed operations should not leave partial state and that stored data should survive a normal upgrade. Clarity means that code, documentation, and interface language should make the next decision understandable. Privacy means that access must be tied to the authenticated owner, not merely hidden behind a screen. Respect means designing neutral failure messages and accessible feedback instead of blaming the user. These values shape both the technical choices in the portfolio and the kind of team I want to join.

Collaboration and Shared Decision-Making

The program changed my understanding of collaboration. It is not limited to dividing code among several people. A collaborative environment depends on work being visible, reviewable, and safe to change. CS 250 introduced that idea through Scrum roles, user stories, acceptance criteria, sprint reviews, and retrospectives. Those exercises taught me to describe work from a user's point of view, identify what “done” means before implementation, and use a retrospective to improve the process rather than assign blame. In an individual course project, I could not claim the experience of shipping production software with a full engineering team. I could still practice the habits that make teamwork possible.

I applied those habits throughout the capstone. Each artifact keeps an unchanged baseline and a separate enhanced version. Decision logs explain why the scope changed. Enhancement maps connect claims to source locations. Verification scripts allow another person to repeat important checks. Read-first files identify the intended review order. These choices reduce the cost of joining a discussion because a reviewer does not have to reconstruct my reasoning from file dates or guess which copy is final.

The refinement from CS 250 planning materials to the CS 320 service suite is one example. My Module One plan initially selected the SNHU Travel planning work for the software design category. During the code review, I determined that the planning documents showed Agile thinking but did not contain enough source code for a meaningful code-level enhancement. I recorded the change instead of silently substituting a different artifact. CS 250 remains evidence of how I think about requirements and stakeholders; CS 320 supplies the technical implementation. In a workplace, that same practice would support a scope conversation with a product owner or reviewer.

Version control and incremental change are also collaboration tools. Work in the program, including the staged architecture of the CS 465 Travlr Getaways application, reinforced the value of separating responsibilities and making changes in reviewable units. My capstone packages follow that principle even when the deliverable is a ZIP: original code, enhanced code, documentation, and evidence have distinct locations. A teammate should be able to challenge one decision without losing the history of the others.

Communication for Technical and Nontechnical Stakeholders

I learned that the same technical choice needs different explanations for different audiences. In CS 465, the Travlr Getaways design served two groups: public customers browsing travel information and administrators managing protected content. The architecture used a public Handlebars site, an Angular single-page administration interface, an Express and Node application layer, and MongoDB behind a shared API. Describing that design only as “a MEAN application” would not explain its value to a stakeholder. The useful explanation is that public browsing and protected administration have different interaction and security needs, while shared routes, controllers, models, and services prevent duplicated business rules.

DAT 205 provided a different communication example. The Two Sisters, Inc. donor analysis required decisions about the reporting period, the meaning of an active donor, geographic scope, privacy, and how results would be presented to a supervisor or stakeholder. The lesson was that analysis can be technically correct and still be unusable if its terms are undefined. Before producing a result, I need to clarify the decision it will support, the data that is appropriate to use, and the limitations that could change the interpretation.

I used those lessons when I organized this ePortfolio. Someone can start with a short explanation of the problem and what I changed, then continue into the complexity notes, schema documentation, diffs, test plans, and source code. I avoided labels such as “optimized” or “secure” unless I could name the exact behavior, the assumptions behind it, and the check that supported it.

Communication also includes interface language. The emerging-technology roadmap for the Weight Tracker proposes goal-aware progress feedback without treating one higher measurement as a personal failure. Color would be paired with text and icons, users could select loss, maintenance, gain, or no goal, and insufficient data would remain neutral. The feature is deliberately labeled as a researched future extension. That distinction gives a stakeholder enough detail to evaluate the idea without confusing a roadmap with implemented functionality.

Data Structures and Algorithms

My algorithms work became more disciplined when I stopped treating the name of a data structure as the justification for using it. A HashMap can provide expected constant-time access by identifier, but that fact does not make a search across all stored values constant time. A user-facing query may require a full traversal, result copying, filtering, and deterministic sorting. The cost depends on the number of stored records and the number of matches.

CS 300 and later coursework developed the habit of comparing structures according to an access pattern. The relevant questions are concrete: Is the common operation an exact key lookup, an ordered range, a prefix search, or a repeated keyword query? How often does the collection change? Is an additional index worth its update and memory cost? What ordering does the caller expect? A structure is appropriate only in relation to those requirements.

In this ePortfolio, exact identifier operations remain map-based while broader contact, task, and appointment queries perform explicit scans and sort only the matches. I document the expected O(1) exact-ID behavior separately from O(c + n + m log m) multi-record retrieval, where c is map capacity, n is stored records, and m is matches. The result lists contain defensive copies and are unmodifiable, so the performance decision does not expose internal state. I also explain why I did not add secondary indexes to a small in-memory collection. An index can be a good future choice without being justified for the current workload.

The same reasoning appears in the database artifact. A compound index begins with user_id because every history query first restricts records to one account. It continues with date and entry ID in the order used by the query. The entry ID provides a deterministic tie-breaker when two measurements share a date. This is a small example, but it shows the full reasoning chain: access pattern, data structure, ordering contract, cost, and executed query-plan evidence.

Software Engineering and Database Design

The strongest change in my software engineering practice is that I now define responsibility boundaries before adding more behavior. In the CS 320 enhancement, models own valid record state, services own collection operations, a shared validator owns repeated input rules, a repository contract defines common operations, and specific exceptions distinguish duplicates from missing records. The services copy records on input and output so callers cannot mutate stored state through an alias. Multi-field changes follow copy, validate, and replace, which prevents a later validation failure from leaving half of an update in memory.

CS 465 reinforced the same principle at a larger scale. Presentation, application, and data concerns belonged in separate layers. Public and administrative interfaces could share an API without sharing every permission. That experience helped me see architecture as a way to protect change. When responsibilities are clear, one layer can evolve without forcing unrelated code to absorb the same decision.

Database work required another level of precision because errors persist. The original Weight Tracker stored usernames as keys, passwords as plaintext, weights and dates as text, and weight rows without a relationship to an account. The enhanced design uses numeric user and entry identifiers, a one-to-many foreign key, numeric weight, normalized dates, constraints, parameterized access, a migration audit table, and ownership-scoped CRUD. The migration preserves what it can prove, isolates ambiguous records instead of guessing an owner, and logs data that cannot be normalized safely.

I also learned to distinguish interface validation from data integrity. A screen should give a useful message before a failed write, but the database should still reject impossible states. NOT NULL, UNIQUE, CHECK, and foreign-key constraints protect the model when a future caller forgets a validation step. That defense in depth makes the schema an active part of the design instead of a passive storage container.

Security Mindset

Security in my work now begins with misuse and failure questions. What happens if a caller keeps a mutable reference? Can one user update another user's row by guessing an identifier? Does registration create an authenticated session without verifying a password? Can malformed stored metadata force excessive computation? Will a database upgrade destroy data? Does the application request a permission it never uses?

The capstone enhancements address those questions in proportion to the artifacts. The Java services validate at defined boundaries, return snapshots, and use specific failure policies. The Android database uses salted PBKDF2 verifiers, constant-time comparison, bounded verifier metadata, randomized inaccessible credentials for blank legacy accounts, parameter binding, authenticated ownership conditions, foreign-key enforcement, disabled database backup, and no unused SMS permission. The work also records unresolved production concerns such as rate limiting, account recovery, encrypted storage, main-thread database access, and a production identity service.

The CS 465 role separation and DAT 205 privacy decisions show that security is not confined to a password class. It includes deciding which audience can perform an action, limiting data to the purpose of an analysis, and explaining sensitive-data handling before implementation. The program taught me to make those questions part of design review rather than wait for a final security checklist.

What the ePortfolio Demonstrates

I put the professional self-assessment first because it explains how I judge my own work. The written code review comes next and identifies the problems in the original projects. After that, the three category pages show the original code, my revised code, the narrative, before-and-after examples, and the checks I ran.

The first technical artifact is the CS 320 Contact, Task, and Appointment Service Suite. Its software design enhancement reorganizes the project, centralizes validation, establishes service contracts, protects state ownership, makes updates atomic at the service boundary, and injects a clock for deterministic date testing. The package contains 97 JUnit methods and a separate 26-check executable verifier.

The second artifact builds cumulatively on that same suite but keeps the category boundary explicit. It adds case-insensitive contact search, keyword task search, inclusive appointment date-range filtering, immutable snapshot results, deterministic comparators, and written complexity analysis. The cumulative project contains 103 JUnit methods, and a focused 19-check verifier exercises the new retrieval contracts.

The third artifact is the CS 360 Android Weight Tracker. Its database enhancement normalizes the schema, establishes record ownership, replaces plaintext password storage, adds migration and auditing, supports ordered history and progress reporting, and verifies the selected index. Forty-six SQLite checks and 36 standalone Java checks passed. Across the three category verifiers, the portfolio records 127 passing executable checks. The number is not a substitute for thoughtful test design, but it makes the scope of the evidence concrete.

Together, the artifacts show how I work across a system. The service suite focuses on in-memory state and API boundaries. The retrieval enhancement shows how access patterns affect algorithms and data structures. The Weight Tracker shows what changes when state becomes persistent, relational, private, and subject to migration. The artifacts are different enough to demonstrate range and connected enough to show a consistent engineering approach.

Alignment With the Five Program Outcomes

Outcome One: Collaborative environments. I employ user stories, acceptance criteria, reviewable scope, versioned baselines, decision logs, traceability maps, reproducible checks, and explicit limitations. These practices let technical and nontechnical reviewers participate in a decision without having to reverse-engineer the work. My artifacts were completed independently, so I do not misrepresent them as a production team project; they demonstrate the habits that make responsible collaboration possible.

Outcome Two: Professional communication. I present the same solution at several levels: user problem, technical decision, source location, test evidence, and limitation. CS 465 and DAT 205 gave me specific practice translating architecture and analysis for different stakeholder needs. The ePortfolio applies that skill through readable web pages, technical narratives, code-review materials, and evidence guides.

Outcome Three: Algorithms and data structures. I select structures according to access patterns, separate exact lookup from traversal and sorting, state time and space costs, establish deterministic ordering, protect returned state, and explain when an additional index is not yet justified. The algorithms artifact and database query plan provide direct evidence.

Outcome Four: Well-founded tools and techniques. I used Java, Maven, JUnit, Android project structure, XML, SQLite, relational constraints, migrations, indexes, Gradle files, cryptographic APIs, verification scripts, diffs, and GitHub Pages. I chose them for specific jobs and checked the behavior they were supposed to support.

Outcome Five: Security mindset. I identify vulnerabilities and failure paths, add multiple enforcement layers, and document residual risk. The strongest evidence is the progression from mutable aliases and vague errors to explicit service boundaries, and from plaintext, account-independent SQLite rows to hashed credentials and ownership-scoped operations. I also treat privacy, accessibility, and honest capability statements as part of secure professional practice.

Employability and Next Development Goals

I am looking for an entry-level application-development role where I can contribute to Java, Android, API, database, testing, or full-stack work. I can read an existing codebase, keep a clean copy of the starting point, choose a manageable improvement, implement it, test it, and explain what I did. I am comfortable moving between what the user sees and what the code is doing underneath.

My next goals are specific. I want more experience with collaborative pull-request review, continuous integration, deployment, background and asynchronous data access, production authentication, and cloud-hosted persistence. For the Weight Tracker, a logical technical step would be moving database work off the activity thread or adopting Room with lifecycle-aware components. For a full-stack project, the next step would be deploying a protected API with automated tests and observable failure handling. These goals extend the evidence in the portfolio instead of replacing it.

This portfolio shows the work I finished, the behavior I tested, and the parts I would still change. I want to be the kind of developer who is careful with an existing system, honest about what the code proves, and willing to revise a design after learning more about the users and their data.
